6. **COLMAP 4.2.1 `sequential_matcher` 기본값이 문제다.** `quadratic_overlap` 기본 1 이면 앞뒤 20장을 다 잇지 않고 **1, 2, 4, 8, ... 2^19 장 떨어진 사진만** 잇는다
   (`controllers/pairing.cc` 580~605행, v3 DB 로 확인). 261장이면 사진당 짝 9개뿐이고 64·128·256장 떨어진 짝이 가짜 짝이 된다.

7. **위치 제약은 복도 축 둘레 기울기를 못 잡는다.** 일직선 동선이면 pose_prior_mapper 결과가 축 둘레로 0.5~36° (나쁜 실행은 최대 175°, 뒤집힘) 기운 채 도면에 놓인다.
   카메라가 축 위에 있어 위치 오차로는 안 보인다. 벽 맞추기(walls·snap)에 직접 영향이 있다.
   짐벌이 수평을 유지한다는 점을 써서 모델을 수평으로 돌린 뒤 제약에 다시 맞추면 기울기 0.1° 가 된다 (아래 "직접 맞춤").
8. pose_prior_mapper 의 도면 좌표 배치는 seed 에 따라 흔들린다 (같은 모델인데 0.5 m 안 98~146장). 직접 맞추면 매번 166장, 중앙 오차 0.31 m, 1 m 넘는 사진 0.
   남는 오차는 그린 동선 자체의 오차다 (제약과 정답의 거리 중앙 0.41 m, 최대 1.63 m).
9. 2차 정합에 제약을 꼭 넣을 필요는 없다. 일반 mapper 로 돌려도 255/0 이고 3배 빠르다 (62~70초 vs 190~240초). 그 뒤 직접 맞추면 도면 좌표가 된다.

열 설명
- 짝 (가짜): mapper 가 쓴 검증된 짝 수와 그중 가짜(정답 F 에 대한 inlier Sampson 오차 중앙값 > 6 px).

- 도면 기울기: 정답의 위쪽 방향이 모델에서 수직에서 벗어난 각도(중앙값).

- 시간: mapper + 거르기(상대 자세 계산은 처음 한 번 47초, 그 뒤는 캐시). 다른 작업과 겹친 실행이 있어 ±30%.

## 3. 왜 이렇게 되나

- SIFT 는 보는 방향이 비슷해야 매칭된다. 그래서 진짜 짝은 상대 회전이 작다. 양 끝이 대칭이면 "갈 때 앞을 본 사진"과 "올 때 앞을 본 사진"이
  같은 자리·같은 방향처럼 매칭된다(실제로는 180° 반대). 카메라가 어느 쪽을 보는지 알면 걸러진다.
- 동선의 진행 방향은 카메라 방향의 근사일 뿐이다. 멈춰서 둘러보거나 끝에서 도는 동안은 틀린다. 그래서 T_rot 은 가짜를 1429개 남긴다.
- 1차 정합은 **실제 카메라 방향**을 준다. 앞뒤 짝만 쓰면 접힐 일이 없고, 끊긴 조각은 위치 제약으로 같은 좌표에 놓인다.
  그래서 조각이 달라도 두 사진의 상대 자세를 예측해 비교할 수 있다.
- 접힌 모델에서 시작하면 안 된다: exhaustive + 제약 결과의 자세로 검증하면(`pose_exh_prior`) 129장. 1차는 깨끗해야 한다.
- 1차 조각도 축 둘레로 기운다 (133장 조각 3.4°, 142장 조각 33°). 그래도 255/0 이 나왔지만, 수평을 맞춘 뒤 검증하면 진짜 짝을 340개 더 살린다.
  1차 조각이 뒤집혀(156°) 놓인 실행도 있었다. 수평 맞추기 + 제약에 다시 맞추기를 넣으면 문제없다 (`prior_verify.load_reference`).
- 제약을 mapper 에 넣는 것은 양날이다. 1차에서는 도움이 됐다 (제약 없이 앞뒤 짝만: 조각 안에서 35장 틀림, 제약 있으면 0).
  하지만 틀린 동선(t2s)에서는 1차가 한 덩어리로 이어지면서 71장이 휘었다. 그래도 제약에서 1.5 m 넘게 떨어진 사진을 기준에서 빼므로 2차는 255/0 이었다.
- 틀린 동선: 고정점 시간 +2초(t2s), 전체 +1 m(x1m) 모두 255/0. x1m 은 모델은 맞지만 도면 위에서 1 m 어긋나 놓인다(동선이 그렇게 그려졌으므로).

## 4. 권하는 순서와 Windows COLMAP 4.2.1 명령

옵션 이름은 4.2.1 소스에서 확인했다: `exe/feature.cc`(matches_importer, spatial_matcher), `exe/sfm.cc`(pose_prior_mapper, mapper),
`controllers/option_manager.cc`(SequentialMatching.*, SpatialMatching.*, Mapper.*), `controllers/pairing.cc`. PC 에서 `-h` 로 한 번 더 확인할 것.

```
set DB=colmap\db.db
colmap feature_extractor --database_path %DB% --image_path frames --ImageReader.single_camera 1 --ImageReader.camera_model OPENCV

:: 1) 앞뒤 20장 짝만. quadratic_overlap 0 이 핵심
colmap sequential_matcher --database_path %DB% --SequentialMatching.overlap 20 --SequentialMatching.quadratic_overlap 0 --SequentialMatching.loop_detection 0

:: 2) priors.json -> DB pose_priors (지금 있는 database.write_pose_priors), 1차 정합
colmap pose_prior_mapper --database_path %DB% --image_path frames --output_path colmap\sparse_pass1 --overwrite_priors_covariance 0

:: 3) 후보 짝 추가 (같은 DB. 이미 매칭한 짝은 건너뜀). 12 m, 이웃 제한은 사실상 없게
colmap spatial_matcher --database_path %DB% --SpatialMatching.max_distance 12 --SpatialMatching.max_num_neighbors 300 --SpatialMatching.ignore_z 1
::    사진이 300장쯤이면 exhaustive_matcher 도 됨

:: 4) DB 사본에서 짝 검증 (파이썬, prior_verify.py). 원본 DB 는 그대로
copy colmap\db.db colmap\db_verified.db
::    ref = load_reference(colmap\sparse_pass1, priors);  verify_pairs(colmap\db_verified.db, ref)

:: 5) 2차 정합 (둘 중 하나)
colmap pose_prior_mapper --database_path colmap\db_verified.db --image_path frames --output_path colmap\sparse --overwrite_priors_covariance 0
colmap mapper            --database_path colmap\db_verified.db --image_path frames --output_path colmap\sparse

:: 6) 가장 큰 모델을 수평 맞추고 제약에 다시 맞춤 (파이썬) -> image_undistorter
```

- 3)의 `max_num_neighbors` 는 0 을 못 쓴다 (`SpatialPairingOptions::Check`: > 0). 사진마다 가까운 순으로 그 수만큼만 잡으므로 크게 준다.
  1084장이면 12 m 안에 수백 장이 들어갈 수 있다. 매칭 시간이 문제면 8 m 로 줄인다 (v4 에서 8 m 도 255/0). 6 m·80장은 부족했다.
- 4) 뒤에는 그 사본에 매처를 다시 돌리면 안 된다. matches 는 있고 two_view_geometries 가 없는 짝을 COLMAP 이 다시 검증해 되살린다
  (`controllers/feature_matching_utils.cc` 642~670행).
- 실제 매처로 끝까지 돌린 확인(`route_cli.py`, 12 m·300장, 1차·2차 모두 제약): **255장 등록, 틀린 사진 0, 순간이동 0.**
  검증에서 가짜 짝 4966 → 93개, 기준 자세 239장(1차 조각 142 + 133장, 제약에서 먼 16장 제외).
  시간: sequential 18초, 1차 정합 211초, spatial 146초, 검증 32초, 2차 정합 196초 (CPU). COLMAP 이 놓은 좌표는 축 둘레로 35.9° 기울었고, 직접 맞추면 0.1°.
  같은 순서를 6 m·80장으로 돌리면 좋은 동선에서 124장만 맞았다 (가짜 짝은 4개뿐. 후보가 모자란 것). 틀린 동선(t2s)에서는 255/0.
- 사진이 4배(1084장)여도 검증 계산은 짝 수에 비례한다. v4 에서 15701짝에 47초(1코어)였다.

## 5. src 에 넣을 설계 제안 (구현은 메인 세션)

새 모듈 `indoorgs/colmap/pair_verify.py` (이 폴더 `prior_verify.py` 가 시험판. numpy + OpenCV + sqlite + `colmap.model` 만 씀):

```python
@dataclass
class Reference:            # 1차 정합에서 얻은 사진별 자세 (도면 좌표)
    poses: dict[str, tuple[np.ndarray, np.ndarray]]   # 이름 -> (R_world_from_cam, 중심)
    K: np.ndarray; dist: np.ndarray; info: dict

def load_reference(sparse: Path, priors: dict, max_far_m: float = 1.5, min_model: int = 10, level: bool = True) -> Reference
    # sparse/<n> 의 10장 이상 모델 모두. 모델마다 수평 맞추기 + 제약에 다시 맞추기. 제약에서 1.5 m 넘는 사진은 뺌. 겹치면 큰 모델 것
def verify_pairs(db: Path, ref: Reference, seq_keep: int = 10, rot_tol_deg: float = 30.0, dir_tol_deg: float = 45.0,
                 min_baseline_m: float = 1.0, drop_unknown: bool = True) -> dict
    # db 의 two_view_geometries 에서 안 맞는 짝 삭제. 통계 돌려줌 (kept, drop_rot, drop_dir, drop_unknown)
def align_model_to_priors(model: cmodel.Model, priors: dict) -> tuple[cmodel.Model, dict]
    # 최종 모델: 수평 맞추기(카메라 오른쪽 축들과 가장 수직인 방향 = 위) + 수직축 회전·축척·이동 강건 최소제곱. 점·카메라 모두 변환
    # (시험판: prior_verify.level_rotation + fit_to_priors, pm.align_to_priors)
```

`stages/register.py` 에 끼우는 자리 (priors 가 있고 `register.prior_verify: true` 일 때만. 아니면 지금 흐름 그대로):

1. `run()` 의 매칭: `OPT_SEQ_QUADRATIC = "--SequentialMatching.quadratic_overlap"` 를 추가해 **항상 0** 으로 준다 (제약이 없어도. 이것만으로도 가짜 짝이 준다).
   prior_verify 일 때는 `rc.matcher` 와 상관없이 1차 매칭을 sequential(overlap, quadratic 0, loop_detection 0)로 한다.
2. `_map()` 을 둘로: `_map_pass1(db, colmap/sparse_pass1)` = 지금의 `write_pose_priors` + `pose_prior_mapper`.
3. 새 `_add_candidates(db)`: `spatial_matcher` (설정 `register.verify_max_distance` 12, `verify_max_neighbors` 300) 또는 `rc.matcher == "exhaustive"` 면 exhaustive.
4. 새 `_verify(db) -> db_verified`: `shutil.copy2(db, colmap/db_verified.db)` 후 `load_reference` + `verify_pairs`. 통계를 `register.json` 의 `"pair_verify"` 에 기록.
   기준 자세가 전체 사진의 절반 미만이면 경고하고 지금 흐름(1차 결과를 그대로 씀)으로 돌아간다.
5. 2차: `pose_prior_mapper --database_path db_verified.db --output_path colmap/sparse` (실패하면 `mapper`).
6. `best_model` 뒤, undistort 앞: `align_model_to_priors` 로 바꾼 모델을 `colmap/sparse_aligned/0` 에 쓰고 그것을 undistort 입력으로.
   `register.json` 에 `"aligned": true` 를 적고, `diagnose.paths_in_plan_coords` 는 `mapper == pose_prior_mapper` 또는 `aligned` 면 도면 좌표로 본다.
7. 완료 표시 파일: `pass1.done`, `matching.done`(후보 추가까지), `verify.done`, `mapper.done`. `prev_targets` 에 `sparse_pass1`, `db_verified.db`, `sparse_aligned` 추가.

주의할 점
- 왜곡: 시험판은 1차 모델의 카메라(SIMPLE_PINHOLE/PINHOLE/SIMPLE_RADIAL/RADIAL/OPENCV)로 특징점 왜곡을 풀고 E 를 구한다. v4 는 SIMPLE_RADIAL 만 시험했다.
- 수평 맞추기는 짐벌(Osmo Pocket 3)처럼 화면이 수평인 영상에서만 맞다. 손으로 기울여 찍은 영상이면 끈다.
- `diagnose` 의 `far_from_prior`(1 m)는 직접 맞춘 뒤에 재야 한다. COLMAP 배치 그대로면 맞는 사진도 14~88장 걸린다.

## 6. 한계 (솔직하게)

- 합성 장면 하나(복도 1개, 261장, 왕복)에서만 확인했다. 실제 영상으로는 아직 안 돌렸다.
- 두 번 정합이 255/0 인 15번은 seed·동선·후보 범위를 바꾼 것이지 장면을 바꾼 것이 아니다.
- 1차가 여러 조각으로 잘게 끊기면(10장 미만 조각, 또는 제약이 3 m 도 안 퍼진 조각) 그 사진들의 떨어진 짝은 모두 지워진다. 그 구간은 앞뒤 짝으로만 이어진다.
- 방(복도가 아닌 곳)에서 제자리에서 한 바퀴 도는 촬영은 시험하지 않았다. 앞뒤 짝만으로 1차가 서는지 봐야 한다.
- 제약 없이 1차를 만들고 조각을 직접 제약에 맞추는 길(`np_pose`)도 253~255장으로 됐다. 다만 1차 조각 안이 덜 정확해서(35장 틀림) 권하지 않는다.
- 같은 짝인데 seed·mapper 종류에 따라 결과가 갈린 실행이 여럿 있다 (T_rot, spatial 6 m). 한 번 돌린 결과로 판단하면 안 된다.

## 실행 방법

`route_cli.py` 는 표를 찍은 뒤 파이썬이 끝날 때 pycolmap 이 죽는 메시지를 낸다 (결과 파일은 이미 쓰인 뒤라 영향 없음).

```
PY=<pycolmap 4.2.1 venv python>; V=<장면 폴더>
$PY render_v4.py $V                                  # 사진 261장 + 정답 + priors (4코어 약 20분)
$PY pm.py --scene $V --runs exh,oracle,exh_prior,seq20_prior,pose_seq20_prior     # 특징·exhaustive 매칭(10분) 후 실행, 표 출력
$PY pm.py --scene $V --stages eval --runs <이름들>     # 표만 다시
$PY route_cli.py $V route_spa12 good 12 300          # 실제 매처로 권하는 순서 끝까지
```
실행 이름과 설정은 `pm.py` 의 `RUNS`. `_s<n>` 을 붙이면 mapper seed 만 바뀐다. v3 장면 폴더에도 그대로 쓸 수 있다 (`--stages map,eval`).
